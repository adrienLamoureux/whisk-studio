Job spine — one record for every generation

How every image, video, illustration, animation and music generation is tracked as one JOB row that the UI resumes from after a reload.

TL;DR

  • Every async generation is one JOB row in DynamoDB, whatever the provider.
  • Status is always queued, running, completed or failed.
  • On load, the UI asks GET /jobs?active=1 and resumes from it. The browser stores nothing.
  • A job can resume only if it carries a poll recipe.

The big picture

Routes write job rows. One feed reads them. The UI resumes from the feed.

What a job row holds

One shape for every provider. Old rows are reshaped when read.

pk / sk
USER#<userId> / JOB#render/<provider>/<kind>/<providerRef>
jobId
job-<time>-<random>. Old rows fall back to the key.
providerRef
The provider's own id: prediction id, invocation ARN or token.
status
One of four values. See the lifecycle below.
poll
Params the provider status route needs. No poll, no resume.
parent
{sessionId, sceneId} for story media, else null.
result
{key, url} once the media is stored.

Status lifecycle

Four states. Provider words are mapped at the boundary and never leak past it.

starting, processing, InProgressrunning
pending, empty, anything unknownqueued

Resume flow

The server knows what is running, so a reload on any device picks the work back up.

  • Image: onResume calls startImagePolling with job.poll.
  • Video: onResume restores the prediction id or invocation ARN, and the poll effects restart.

Adding a job producer

Use the job store, store a poll recipe, and settle the job when it ends.

  1. Create the job when work starts Call deps.jobStore.createJob with kind, provider and providerRef.
  2. Store the poll recipe Pass meta: { poll } with every param your status route needs.
  3. Settle it Call updateJob with completed and a result, or failed and an error.
  4. Resume in the UI Call useResumableJob with your kind and re-arm the poll in onResume.

Gotchas

Known traps, found while reading the code at commit 617a159.

Bedrock video jobs never settle

The Nova Reel status route never updates the job row. The row stays running in the active feed.

So a finished job may resume on every page load. inferred

CivitAI cannot resume

CivitAI rows have no poll, so the resume hook skips them.

getJob is a scan

It loads up to 500 jobs and filters in memory. There is no direct lookup by jobId.

updateJob rewrites the row

Pass the job you just read. Fields missing from it are lost.
